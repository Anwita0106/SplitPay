# SplitPay AI Agent

SplitPay AI is a free, local assistant built **on top of** the deterministic financial backend. It is an
orchestration layer: it understands a request, calls backend services, and reports what they returned.
It is never a source of financial truth.

## Stack

- Ollama for local inference, default model `qwen2.5:3b` (`OLLAMA_BASE_URL`, `OLLAMA_MODEL`)
- FastAPI controller: `app/api/routes/agent.py`
- Agent logic: `app/services/agent_service.py`
- Confirmation gate: `app/services/draft_service.py` + the `ai_actions` table
- PostgreSQL is the source of truth; `Decimal` math and the canonical balance engine stay authoritative

## Request flow

```text
React /ai
  -> POST /ai/chat  {message, conversation, group_id?}
  -> agent_service.chat
       1. deterministic intents (AI_DETERMINISTIC_INTENTS=true): balances, spending,
          "I paid ... with ...", "settle ..." are parsed by backend code
       2. otherwise the Ollama tool-calling loop (max 6 rounds)
  -> tools  ->  group_service / balance_service / draft_service  ->  PostgreSQL
  <- reply text rendered from backend data (+ optional draft or clarification)
```

Because step 1 does not need the model, balance questions, expense drafts and settlements phrased directly
keep working when Ollama is down. Anything else returns a friendly "start Ollama" message.

## Tools

| Tool | Kind | What it does |
|---|---|---|
| `list_groups` | read | the user's groups (id, name, members) |
| `get_my_balances` | read | the user's position in every group, already phrased ("Anwita owes you ₹1200 in Goa Trip.") |
| `get_group_summary` | read | members, recent expenses, balances of one group |
| `get_spending_summary` | read | totals paid / share per group |
| `get_settlements` | read | settlements involving the user |
| `prepare_expense_draft` | draft | validates and **stores a PENDING draft**; nothing is written to `expenses` |
| `prepare_settlement_draft` | draft | same, for a settlement; refuses impossible amounts |

There is **no** tool that creates, confirms, edits or deletes anything (`test_agent_has_no_write_or_confirm_tool`
enforces this, and unknown tool names are refused).

## Confirmation gate

```text
prepare_*  ->  ai_actions row (PENDING, server-built payload, expires in AI_DRAFT_TTL_MINUTES)
user clicks Confirm  ->  POST /ai/drafts/{draft_id}/confirm      (no body)
  -> load the draft scoped to the caller (someone else's draft == "not found")
  -> row-lock it; already CONFIRMED -> return the first result (idempotent, never a second write)
  -> expired / cancelled / failed -> 409
  -> RE-VALIDATE against current data and write via the normal expense / settlement service
  -> mark CONFIRMED in the SAME transaction
```

- The confirm endpoint executes the payload **the backend stored**. A tampered client request cannot change
  what is written; the LLM cannot confirm anything.
- If data changed since the draft was prepared (a member left, the debt was already settled) the draft is
  marked `FAILED` with the reason and nothing is written.
- Typing "yes" / "confirm" in the chat never saves anything; the reply points at the Confirm button.
- Deleting a group cancels its pending drafts. `GET /ai/actions` lists a user's drafts and outcomes.

## Group and people resolution

- `group_service.resolve_group` is the only name lookup. It accepts a UUID, a name (exact → word match →
  typo-tolerant) and an optional UI-chosen `group_id`. A UUID that isn't the user's is "not found".
- If the model puts the group *name* in the `group_id` argument it is treated as a name, not an error.
- **Two groups with the same name are never guessed between.** The response carries a `clarification` with one
  button per candidate (name, members, created date, expense count); choosing one re-sends the message with
  that `group_id`.
- `resolve_person`: "you", "me", "myself" and the user's own name are one person, so `["Anwi", "Anwita", "You"]`
  becomes two participants. A first name matches a full name only when unambiguous. Unknown names are an
  error — the agent never invents a user.

## Settlements by AI

A settlement draft can be started by **either party** of the debt ("I want to settle the ₹1200 Anwita owes me"
or "I paid Anwita ₹500"). Confirming records it as **paid outside SplitPay** (`method=MANUAL`, `COMPLETED`), which
immediately updates balances. Paying through UPI still goes through the Settlements page and the payment /
webhook flow. Amounts are validated by `settlement_service.validate_settlement` against current balances,
including in-flight UPI payments.

## Guardrails on wording

Replies are rendered from backend data with `format_inr` (never a signed number). When a draft exists the reply is
generated by the backend, so a model that claims "I saved it" or invents an amount cannot leak into the UI.

## Local setup

```bash
ollama pull qwen2.5:3b        # Ollama must be running on the host
docker compose up --build     # Docker Desktop reaches the host at host.docker.internal
```

Open `http://localhost:5173/ai` after logging in.

## Security boundary

```text
React -> POST /ai/chat -> agent controller -> (Ollama | deterministic parser)
      -> read / prepare tools -> PostgreSQL
React -> POST /ai/drafts/{id}/confirm -> draft_service -> expense / settlement services -> PostgreSQL

The LLM never receives credentials, never runs SQL, and has no confirm tool.
```
